# Корпоративная система квестов для сотрудников

## Предметная область

На этапе предпроектного обследования руководитель производственного отдела
предоставил сведения: «Мы хотим выдавать сотрудникам задания (квесты) через
телефон. Каждое задание может требовать списания материалов со склада.
Разные задания имеют разную срочность, и менеджеру нужно видеть, кто и что
сейчас выполняет, а сотруднику — не нужно разбираться в сложной админке,
ему нужно открыть телефон и понять, что делать прямо сейчас».

- Для менеджера производства это операционные параметры (кто свободен,
  чего не хватает на складе, что горит по срокам).
- Для инженера-программиста (SWEBOK) — это входные данные, под которые
  нужно спроектировать систему с двумя разными интерфейсами (админ-панель
  и мобильное приложение) и надёжной интеграцией со складским учётом.

Если жёстко зашить в код фиксированный список материалов, один список
приоритетов и один сценарий «выдал — сотрудник закрыл», система не
переживёт первое изменение номенклатуры склада или структуры отдела.

Главная задача: перевести операционные параметры предметной области в
спецификацию функциональных требований (FR), нефункциональных требований
(NFR) и системных ограничений (Constraints).

## Шаг 1. Матрица стейкхолдеров и прав доступа

| Функция системы | Сотрудник | Менеджер | Кладовщик | Системный аналитик |
|---|---|---|---|---|
| Просмотр и выполнение назначенных квестов | Да | Да | Нет | Нет |
| Создание квестов и назначение приоритета | Нет | Да | Нет | Нет |
| Просмотр остатков материалов | Да (только по своему квесту) | Да | Да | Нет |
| Списание/пополнение материалов на складе | Нет | Нет | Да | Нет |
| Просмотр общего прогресса по отделу | Нет | Да | Нет | Да |
| Настройка ролей и прав доступа | Нет | Нет | Нет | Да |
| Настройка интеграции со складской системой (API) | Нет | Нет | Нет | Да |
| Просмотр логов операций (Event Log) | Нет | Нет | Нет | Да |

**Архитектурное противоречие:** менеджеру нужна аналитика по прогрессу
всех сотрудников и истории списаний материалов (тяжёлые агрегирующие
запросы), а сотруднику на телефоне нужен мгновенный отклик простого
интерфейса «мои задачи». Если строить отчёты в той же БД, где сотрудники
в реальном времени закрывают квесты и списывают материалы, приложение
будет тормозить в пиковые часы (начало и конец смены).

**Разрешение аналитика:** разделить систему на два контура: транзакционный
контур (мобильное приложение сотрудника + операции со складом, OLTP) и
контур аналитики/отчётности для админ-панели менеджера (OLAP), связанные
асинхронно через очередь событий (event-driven, CQRS).

## Шаг 2. Функциональные требования (FR)

### Модуль А: Квесты и приоритеты (Task & Priority Engine)

| ID | Требование |
|---|---|
| FR-01 | Система должна предоставлять Менеджеру интерфейс создания квестов с полями: название, описание, срок выполнения, ответственный сотрудник/группа. |
| FR-02 | Система должна поддерживать не менее 4 уровней приоритета (Низкий/Средний/Высокий/Критичный) с визуальной индикацией (цвет/иконка) в интерфейсе сотрудника. |
| FR-03 | Система должна позволять Менеджеру переназначать квест на другого сотрудника без потери истории выполнения. |
| FR-04 | Система должна поддерживать создание шаблонов повторяющихся квестов (например, ежедневный чек-лист). |

### Модуль Б: Интеграция с инвентарём (Inventory Sync Module)

| ID | Требование |
|---|---|
| FR-05 | Система должна отображать сотруднику остаток материалов, привязанных к его квесту, в реальном времени. |
| FR-06 | Система должна автоматически резервировать материал за квестом при его назначении и списывать при закрытии. |
| FR-07 | Система должна отправлять Менеджеру уведомление при падении остатка материала ниже установленного порога. |
| FR-08 | Система должна поддерживать сканирование QR/штрихкода материала камерой телефона для подтверждения списания. |

### Модуль В: Прогресс и отчётность (Progress & Admin Module)

| ID | Требование |
|---|---|
| FR-09 | Система должна отображать Менеджеру дашборд прогресса (% выполнения, просроченные квесты) по каждому сотруднику и отделу в целом. |
| FR-10 | Админ-панель должна предоставлять Kanban-доску («Новое / В работе / Готово») с drag-and-drop для управления квестами. |
| FR-11 | Система должна отправлять push-уведомление сотруднику при назначении нового квеста или изменении его приоритета. |
| FR-12 | Система должна формировать выгрузку отчётов (Excel/CSV) по выполненным квестам и расходу материалов за период. |

## Шаг 3. Нефункциональные требования (NFR) на базе ISO 25010

| Категория ISO 25010 | Контекст предметной области | Инженерная формулировка требования |
|---|---|---|
| Performance Efficiency | Начало смены — все сотрудники одновременно открывают список квестов. | NFR-01: Время загрузки списка квестов на мобильном клиенте не должно превышать 1.5 сек при 200 одновременных запросах. |
| Performance Efficiency | Менеджер строит отчёт по остаткам за месяц. | NFR-02: Формирование отчёта по складским операциям за период не должно занимать более 5 секунд для выборки до 50 000 записей. |
| Reliability | Сбой синхронизации со складом не должен останавливать выдачу квестов. | NFR-03: Модуль квестов должен сохранять работоспособность в режиме деградации при недоступности сервиса инвентаря (Circuit Breaker), Availability ядра — не менее 99.5%. |
| Usability | Сотрудник работает в перчатках/на ходу, интерфейс должен быть предельно простым. | NFR-04: Основной сценарий сотрудника (открыть квест → отметить выполнение) должен укладываться не более чем в 3 нажатия. |
| Usability | Менеджеру нужен полный контроль без визуального шума у сотрудника. | NFR-05: Админ-панель и мобильный интерфейс сотрудника реализуются как раздельные UI-модули с независимой навигацией. |
| Maintainability | Складская система (1С, WMS) может меняться или обновляться независимо. | NFR-06: Интеграция с инвентарной системой должна быть изолирована через паттерн «Адаптер» и покрыта unit-тестами не менее чем на 80%. |
| Security | Сотрудник не должен видеть данные чужих отделов и полную складскую аналитику. | NFR-07: Система должна реализовывать ролевую модель доступа (RBAC) с проверкой прав на уровне API для каждого запроса. |
| Security | Списание материалов — финансово значимая операция. | NFR-08: Каждая операция списания/пополнения материала должна логироваться с указанием пользователя, времени и quest-ID (неизменяемый журнал). |
| Compatibility | У компании уже есть складской учёт, систему квестов делают отдельно. | NFR-09: Обмен данными об остатках должен происходить через REST API/Webhook без прямого доступа к БД складской системы. |
| Portability | Сотрудники используют разные модели телефонов (Android/iOS). | NFR-10: Мобильное приложение должно поддерживать актуальные версии Android и iOS без потери функциональности (кроссплатформенный фреймворк). |

## Шаг 4. Системные ограничения и допущения (Constraints)

- **Constraint-01 (Платформа):** В v1.0 система реализуется только как мобильное приложение для сотрудников (Android/iOS) и веб-панель для менеджера; десктоп-клиент не разрабатывается.
- **Constraint-02 (Оффлайн-режим):** Полноценная работа без сети не поддерживается; допускается только отложенная синхронизация отметок о выполнении при кратковременной потере связи (очередь на устройстве).
- **Constraint-03 (Интеграция со складом):** Поддерживается только интеграция через REST API/Webhook с одной внешней системой учёта; прямое подключение к оборудованию (RFID-считыватели, весы) в v1.0 не реализуется.
- **Constraint-04 (Мультиарендность):** Система проектируется для одной организации (single-tenant); поддержка нескольких независимых компаний в одном инстансе не предусмотрена.
- **Constraint-05 (Локализация):** Интерфейс v1.0 реализуется только на русском языке.
- **Constraint-06 (Технологический стек):** Для хранения квестов и остатков материалов используется СУБД с поддержкой ACID-транзакций (например, PostgreSQL), чтобы исключить рассинхронизацию остатков при одновременном списании.
- **Constraint-07 (Часовой пояс):** Система рассчитана на работу в пределах одного часового пояса организации; поддержка распределённых по времени филиалов не реализуется.
